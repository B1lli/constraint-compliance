# 方法说明：使用时刻把一条已学规矩编译成可核对的目标

> 池光耀（Guangyao Chi），2026-09。本文是 `SKILL.md` 背后的方法陈述：我们主张什么、哪些是借的、怎么量的、量到了什么、还差什么。
> 判定词只用三个：PASS / FAIL / UNPROVEN（原因）。

## 一、问题：教过，但没教会

一个会自进化的 Agent，最朴素的一环是「用户纠正一次，以后都照做」。做到「记住」并不难：写进 `CLAUDE.md` / `AGENTS.md`、写进记忆文件、
或像我们的产品那样从对话里自动提炼成**学习项**并在相关时召回。难的是**记住之后照做**。

我们在 2026-08 对 270 个生产用户的会话做过一次「掉遵循」审计：14 个可归因事件里，10 个的形状是**规矩用户早就教过、注入后模型也「知道」、
长任务后期照样掉**；同一用户同一规矩的复发占了 3 个。文献同向：

- 五轮对话内，顶级模型对系统消息的会话稳定率只有 51.8%–54.4%；GPT-4o 在依赖型多轮里第 1 轮 84.8% 掉到第 5 轮 33.7%（SysBench，ICLR 2025）。
- 模型能逐字复述它正在违反的约束，七个模型的「知而违」率 8%–99%；每轮自动监测几乎无效（DriftBench，2026-04）。
- 没有外部反馈的自我修正常常更差（Huang 等，ICLR 2024）；「再检查一遍」不解决问题。
- 有效的是**把规矩重新放到靠近生成的位置**（PrefEval 一句提醒把 10 轮偏好遵循从约 13% 拉到约 99%）与**把指令拆成逐项可核清单再逐项验**
  （RLCF，NeurIPS 2025；DVR，ACL 2025，Mistral-7B 24%→73%）。

所以问题拆成两半：**① 在对的那一轮想起规矩**（时机）；**② 想起之后真被守住**（生效）。本 skill 两半都碰，但重心在 ②，① 只由一句极短的 description 承担。

## 二、方法：六步，全部由主 Agent 在原始上下文里做

| 步 | 输入 | 处理 | 输出 |
|---|---|---|---|
| 1 三问值不值 | 当前请求 + 在场的已学规矩 | 有没有一条不该违反的规矩？做错了谁付什么代价？有没有可核对的产物？任一答「不」即退出 | 继续 / 退出（零成本） |
| 2 意图五行 | 对话、附件、已召回规矩 | 写出交付物、消费者、成功信号、非目标、错一次的代价；写不出的写「未知」 | `intent` |
| 3 选档 | 代价、复发、对外性 | L2 只附自检清单；L3 立目标 + 独立评估建议；L4 对外 / 合规 / 资金 / 复发时独立评估必做；拿不准取 L3 | `level`、`precision` |
| 4 写 rubric | 规矩原文 + 本次材料 | 每条一句可判断言 + 判法 + 证据类型 + 硬/软 + 来源；专名必须有字面来源；禁空话；每条能从产物判出；≤12 条；多规矩合并；抱怨过的置顶标硬 | `rubric.criteria` |
| 5 立目标 | 以上 | 写 `.gate/goal.json`（`status: active`），在重活开始之前；能判死的标准挂 `validator` | 目标文件 |
| 6 收尾礼仪 | 产物、目标文件 | 把「已完成」当未证明逐条核；「每条 / 全文」类先列清单再普查；跑确定性核对；起只读独立评估者；硬标准 fail / unverifiable 默认继续干；连续三轮同一阻碍才 blocked | `complete` + `evidence`，或 `blocked` + `reason` |

三条贯穿全程的立场：

1. **判断归有完整上下文的主 Agent。** 值不值、选多强、标准怎么写、建议采不采纳，都不交给关键词表、不交给独立上下文里的小模型、不交给代码终裁。代码与独立评估者只配**提醒**。
2. **决定在信息最全的使用时刻做，不在教学时预设。** 教学那一刻不可能预知未来所有场景，预设档位还加重学习负担。规矩在教学时只保留原话与粗题目；档位、精确化、rubric 全部在用的时候长出来。
3. **越强越贵，只在值得时付。** L2 约等于零成本；L3 多一次评估与若干返工；L4 多一个独立会话。三问就是收费闸。

## 三、与先例的关系：哪些是我们的，哪些是借的

同形状的先例（2026-09-06 检索，范围与未核项见文末）：

| | OpenAI Codex `/goal`（2026-04-30） | Claude Code `/goal`（2026-06） | Claude Managed Agents Outcomes（2026-05） | 本方法 |
|---|---|---|---|---|
| 目标 / rubric 从哪来 | 用户手写 objective | 用户手写条件（≤4,000 字符） | 开发者手写或上传 rubric | **从已学规矩 + 意图洞察在使用时生成** |
| 什么时候触发 | 用户输入 `/goal` 或模型调 `create_goal` | 用户输入 `/goal` | 开发者配置 | **请求命中用户教过的规矩且本轮要交付，由 Agent 判断** |
| 谁判完成 | 同一模型自审（续行模板里的完成审计） | 独立小模型，只看对话不读文件 | 独立 grader，读产物 | 主 Agent 审计 + 确定性核对 + **独立评估者读产物、只建议** |
| 档位 | 无 | 无 | 无 | **L2 / L3 / L4 由 Agent 使用时定** |

**据此我们认为属于本团队独立提出的**：

- 触发源是「用户教过的规矩在场 + 本轮要交付」，而不是用户显式下令或开发者预配置；
- 验收标准与目标**从已学规矩加意图洞察在使用时刻生成**，配一套让它可复现的写法规则（专名字面来源、禁空话、可从产物判、≤12、合并、抱怨项置顶）；
- 强度档位由主 Agent 在使用时决定，复发升档；
- 评估器与确定性校验器**只建议不阻塞**，但 Agent 必须回应；
- 计量纪律 fail-closed：挂了校验器却判不出来 = UNPROVEN ≠ 通过；一条校验器都没挂 = 「没核」≠ 通过；抽查一处 ≠ 普查。

**明确借用并致谢**：目标循环与「完成审计」段的措辞取自 Codex `/goal` 的续行模板（把完成当未证、逐条找权威证据、窄检查不撑宽结论、连续三轮同一阻碍才 blocked）；
「规矩拆成逐项清单再验」与 RLCF / DVR 同源；「判官必须能读产物」与 Agent-as-a-Judge（ICML 2025）一致；「完成必须带证据」与 Evidence-Carrying Termination（2026-08）同向。

**不借**：只看对话的小模型判官当唯一判官；代码终裁的契约强制；关键词触发；每轮自动扫描违规。

## 四、与「自进化」的关系

这里的自进化不改权重。进化发生在两处：**持久化的已学规矩**（用户纠正一次就留下痕迹），和**使用时刻的编译**（每次交付前把痕迹重新编译成这一次的验收标准）。
记忆系统解决「记住」，本方法解决「记住之后照做」，两者是互补关系：没有前者，第四类情境（Agent 自己识别的外部要求）以外无从触发；没有后者，
记住的规矩在长任务里照样掉。复发升档让同一条规矩在被违反后自动变贵、变硬，这是这条环里唯一「越用越强」的地方。

## 五、怎么量、量到了什么

**装置纪律**：夹具正文不得自曝测试意图（「这是验收用的合成材料」会让模型改变判断，两个方向都污染）；每个 validator 有正控（合格产物必须过）与负控（每个突变必须让点名那条变红）；
description 改动过「过拟合尺子」（与用例原话的重合度），照抄用例原话的一版必须判红；UNPROVEN 是一等结论，不并入 PASS 或 FAIL；真模型读数在共享网关上串行取。

**三个宿主**：Codex CLI（多轮 resume）、Claude Code（`claude -p` 多轮）、生产真栈（学习项自动生成 → 召回 → 送达 → skill 在清单里）。

**触发（问题 ①）读数**：

| 读数 | 结果 | 判定 |
|---|---|---|
| Claude Code，description 只剩一个信号「命中教过的规矩」，规矩只在 `CLAUDE.md` 或本机记忆里、原话不复述，三个自拟场景 | 正例 **11/12** 在该触发的那一轮调起 skill；阴性 **0/2** 误触发；产物 **12/12** 守住 | PASS（Claude Code 宿主可行） |
| 同一正文配 683 字符的长 description，真实事故复刻用例 RC-01 | **0/11** | FAIL（长描述触发不了） |
| 可选 skill 从 18 条增到 33 条（短描述、完整送达） | 2/2 → 0/2 | 方向成立，样本 2 |
| 生产真栈，规矩确实送达的正例 | **1/4** 调起 skill；阴性 0/1 | 部分可行，卡在触发这一格 |

**生效（问题 ②）读数**：五个合成场景在 Codex 与 Claude Code 上不装 skill 的基线全绿（120–180k 上下文、压缩 4–6 次），说明合成场景推不进真实失守区间；
真实事故复刻用例 RC-01 在基线臂上从未整份全绿，装上 skill 且真的照着做完的那一次整份全绿。**「调了」和「照着做完」是两件事**，本方法只能保证前者带来后者的机会。

**两条与描述无关、两个宿主都出现的事实**：规矩送达 ≠ 规矩被遵循；skill 触发 ≠ 产物合格（反过来没触发也可能合格）。四种组合都实测到了。

## 六、已知局限

1. 触发靠一句 description，对宿主的 skill 清单长度与描述预算极敏感；生产真栈上送达成立的正例只有 1/4 触发，原因未拆（四个变量同时变，UNPROVEN）。
2. 评估器只建议；一个铁了心要交付的 Agent 可以无视它。这是设计选择（不加用户心智负担、不做代码终裁），代价如上。
3. 确定性校验器只覆盖 11 种可判死的形状；语义标准全靠审计与独立评估。
4. 正文是中文（description 中英双语）。英文正文版未做、未测。
5. 生效侧的 A 档证据（基线红、装门绿、多次复现）目前只有一条真实事故复刻用例，样本小。

## 七、术语表

- **学习项**：从用户纠正里持久化下来的一条规矩（我们产品里的叫法）；在别的宿主对应记忆文件或规矩文件里的一条。
- **三问**：有没有不该违反的规矩 / 做错了谁付什么代价 / 有没有可核对的产物。
- **意图五行**：交付物、消费者、成功信号、非目标、错一次的代价。
- **L2 / L3 / L4**：自检清单 / 立目标 + 评估建议 / 立目标 + 独立评估必做。
- **精确化（precise / coarse）**：逐条按写法规则写 rubric，或直接沿用学习项自带的粗题目。
- **收尾礼仪**：标完成前的审计、普查、核对、评估与对建议的回应。
- **「全都要」普查**：带「每条 / 全文 / 所有」的标准先列对象清单再逐个核，抽查不算。
- **UNPROVEN**：没核到、没跑到、前提不成立；不是 PASS 也不是 FAIL。
